# AnkiFlutter First Desktop Vertical Slice Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first usable AnkiFlutter desktop slice: launch a modern Flutter app, load the official Anki Rust backend, open a real `.anki2` collection, show the real recursive deck tree with New/Learn/Review counts, and open a minimal deck overview.

**Architecture:** Flutter owns presentation and small constructor-injected controllers/repositories. A thin Rust `cdylib` owns `anki::backend::Backend` from a pinned upstream Anki checkout. Dart uses protobuf message classes generated from the same pinned Anki proto files; Rust isolates unstable service/method indices and dispatches bytes through Anki's existing `Backend::run_service_method()`.

**Tech Stack:** Flutter 3.47.5 / Dart 3.13.4; `ffi` 2.2.0; `protobuf` 6.1.0; `fixnum` 1.1.1; `file_picker` 13.1.0; Rust 1.80+; official `ankitects/anki` commit `a5a0e444677a6b58cf784a9c2b7c2d5167f20df0`; Protocol Buffers.

**Spec:** `docs/superpowers/specs/2026-09-24-anki-flutter-frontend-design.md`

## Global Constraints

- Flutter is the frontend.
- Initial platform targets are Windows, macOS, and Linux. This first slice fully verifies Linux and keeps handwritten Dart/Rust code platform-neutral.
- Official Anki backend behavior is reused instead of recreated.
- No frontend scheduler, FSRS implementation, direct SQLite writes, or alternate collection format.
- Upstream Anki is pinned to an exact commit; never build releases from floating `main`.
- Upstream service instability is confined to the native bridge/generated protobuf layer.
- Generated protobuf objects never appear in widgets or feature state.
- Every handwritten behavior follows strict RED -> verify expected failure -> GREEN -> full relevant suite -> refactor -> suite again.
- Generated code and unavoidable build/platform configuration are the only TDD exceptions.
- Tests use temporary/disposable collections only.
- Python/PyQt add-on compatibility is out of scope.
- Repository/distribution must comply with AGPL-3.0-or-later obligations inherited from Anki.

## Review Focus

1. **Missing/malformed native backend** -> actionable frontend startup error, never a process crash. Covered in Tasks 5 and 9.
2. **Invalid/corrupt collection** -> failed open leaves app in a clean non-open state. Covered in Tasks 6 and 10.
3. **Nested decks** -> hierarchy and upstream counts are preserved exactly, never flattened/recomputed. Covered in Tasks 7 and 9.
4. **Upstream service/method reordering** -> indices are generated by descriptor name, never handwritten. Covered in Tasks 3 and 10.
5. **FFI ownership** -> every returned native buffer is copied once and freed once on success and all error paths. Covered in Tasks 4 and 5.

### Task 4: Wrap official `anki::backend::Backend` and expose a safe C ABI

**Files:** `src/backend.rs`, `src/ffi.rs`, `src/lib.rs`, `tests/backend_lifecycle.rs`, `tests/ffi_contract.rs`.

**Produces:**

```text
anki_bridge_create(init_ptr, init_len) -> BridgeCreateResult
anki_bridge_invoke(handle, operation, input_ptr, input_len) -> BridgeCallResult
anki_bridge_free_buffer(ByteBuffer)
anki_bridge_destroy(handle)
```

Own operation ids are stable and frontend-defined: `1=open`, `2=close`, `3=deck_tree`. Status: `0=success`, `1=upstream BackendError protobuf`, `2=bridge UTF-8 error`.

- [ ] **Step 1: RED — backend lifecycle**

Tests first:

```rust

#[test]

```

Run `cargo test --test backend_lifecycle`; verify expected RED.

- [ ] **Step 2: GREEN — backend wrapper**

`BridgeBackend` owns `anki::backend::Backend`. `from_init_bytes()` calls only `anki::backend::init_backend()`. `invoke(OperationIndex, bytes)` calls only `Backend::run_service_method()` and preserves upstream error bytes unchanged.

- [ ] **Step 3: RED — ABI ownership/error contract**

Tests first for:

```text
malformed init -> status 2, null handle, UTF-8 error buffer
null handle -> status 2
unknown operation 999 -> status 2
success buffer preserves bytes
backend error buffer preserves bytes
all non-empty buffers are freeable by anki_bridge_free_buffer
```

- [ ] **Step 4: GREEN — exact ABI structs**

```rust
#[repr(C)]
pub struct ByteBuffer { pub ptr: *mut u8, pub len: usize, pub cap: usize }
#[repr(C)]
pub struct BridgeCreateResult { pub status: u32, pub handle: *mut BridgeBackend, pub data: ByteBuffer }
#[repr(C)]
pub struct BridgeCallResult { pub status: u32, pub data: ByteBuffer }
```

Use `ManuallyDrop<Vec<u8>>` to transfer ptr/len/cap and `Vec::from_raw_parts()` only inside `anki_bridge_free_buffer()`. Null pointer with non-zero length is status 2. No panic crosses C ABI: each exported function uses `catch_unwind()` and converts panic to status 2.

- [ ] **Step 5: Verify/commit**

```bash

cargo clippy --all-targets -- -D warnings
cargo fmt --check
git add native/anki_bridge
git commit -m "feat: expose official Anki backend over safe C ABI"
```
